# Browser integration contracts

The original FastAPI backend and its clinical/Pydantic contracts remain unchanged. This static application does not require a remote backend or the owner's computer. Its private SQLite database exists only in the biomedical worker and in encrypted local exports/storage. This is a synthetic-data research application, not an authorized clinical executor.

## Biomedical worker boundary
`src/worker.js` accepts `{id, action, data}` and returns `{id, result, seconds}` or `{id, error}`. Requests are serialized. `seconds` measures worker dispatch execution, not network download, GPU inference or total UI latency. Errors are failures, never normal clinical results. Unlock binds one profile and browser-mission; supplied foreign identifiers are rejected. Successful writes must be followed by encrypted persistence before the UI confirms saving.

Public read-only metadata: `clinical_schema`, `verify_corpus`, `search`, `parity`. Clinical schema adds `derivation_inputs` and `input_metadata_source` without removing existing fields. The dependency map is extracted as a literal from byte-identical `vigile.clinical_engine.evaluate_condition`, with its source SHA-256. It is input-form metadata, not a JavaScript implementation of medical logic. Unrecognized source layout blocks metadata generation.

Private actions after `init_profile`: `evaluate`, `history`, `serialize`, `statistics`, `parse_observation`, `voice_policy`, `save_observation`; plus `ingest`, `baseline`, `trend`, `monitor`, `replay_monitor`, `episode_open`, `episode_transition`, `followup_plan`, `followup_review`, `mission_context`, `inventory`, `timeline`, `replay_clinical`, `management_record`, `countermeasures`, `prevention_add`, `prevention_list`, `radiation_add`, `radiation_import`, `radiation_list`, `radiation_integrate`. Their input objects are validated by the original Python models/services or the dedicated normalizers. See src/browser_monitoring.py, original engine/vigile/models.py and monitoring_models.py for exact biomedical types, `engine/vigile/prevention.py` for the additive self-report and USDA food composition record schema, and `engine/vigile/dosimetry.py` for radiation quantities. `radiation_import` accepts an all-or-nothing batch of at most 10,000 already parsed rows, rejects duplicates against stored and current batch keys, then appends each validated record to the local audit.

## Preventive experience and external integrations

Routes added in More navigation: `exercise`, `nutrition`, `sleep-recovery`, and `wellbeing`. All records are written through `prevention_add` and read using `prevention_list`; encrypted persistence is committed before the UI confirms success. In the disposable demo, manually entered entries are marked synthetic and remain in temporary memory. Exercise checkpoints carry `{training_session:{session_id,plan_id,title,workout_type,status,started_at,updated_at,segment_started_at,elapsed_seconds,current_activity_index,activities:[{exercise_id,sets_completed,repetitions,duration_seconds,workload_note}]}}`; status is one of IN_PROGRESS, PAUSED, STOPPED, COMPLETED. Repeated checkpoints append records; readers deduplicate on `session_id` and choose the latest. Restored IN_PROGRESS records are paused until the user resumes; elapsed time while the app is not active is not added. The UI tracks time between user-controlled start/resume and pause/stop, not sensor-measured activity. Optional perceived exertion is stored as a self-rating only; it is not an intensity recommendation or physiological measurement.

Meal estimates accept only an FDC ID present in the hash-verified offline USDA subset plus `quantity_g`. The worker resolves nutrient values from the same packaged catalog and records provenance; browser-provided nutrient numbers are ignored. Missing database values remain null. Hydration is a user-entered mL record without a target. Sleep supports timezone-qualified `sleep_start` and `sleep_end`, validates the derived integer duration, and stores optional subjective quality (`subjective_quality_1_5`) and fatigue (`fatigue_rating_0_10`); both remain self-reports. Client-side `dailyMealTotals` aggregates only complete per-nutrient source values: when any logged portion lacks a nutrient, `complete_estimated_total` is null and `known_sum`/missing counts are explicitly partial, never zero-filled. `dailySumSeries` aggregates hydration by explicit UTC calendar day without a target or interpretation. The `timeline` action merges already-recorded clinical evaluations and supported observations into one descending event list; it does not derive new clinical results. Well-being ratings/notes are optional local self-reports, not a screening questionnaire or diagnosis.

Radiation CSV input uses a strict header in `src/radiation-csv.js`; valid rows keep their submitted quantity, unit, mode and source, and remain sensor-unverified. A `MEASURED` source label does not imply hardware authenticity. DONKI in-app notices filter types, deduplicate by type+event ID, record local acknowledgement timestamps, and operate only while viewing live or cached public data. No browser background-notification or personal warning contract exists.

`evaluate` receives `{snapshot:{request,mission}, use_registered_context:true}` in Astronaut View. The result preserves `{output,snapshot,input_hash,output_hash,knowledge_hash,...}`. `output.results[condition]` retains diagnostic_status, confirmation_status, urgency, missing_required, optional_not_measured, invalid_required, required_for_protocol_safety, protocol_status, full criteria traces and original scientific references. Do not merge these independent concepts into one missing-fields list. Missing measurements cannot become normal. Meeting criteria is not a signed diagnosis. Protocol/resource availability does not authorize execution.

Persistent profiles start without fabricated observations, population, age or assessment window. Saved clinical inputs remain historical, owner-bound and editable as a new draft. Dashboard cards show recorded profile data with self-reports explicitly separated from measurements. The initial synthetic mission bootstrap is Earth/in-mission; operators must review mission context. It is not verified spaceflight context. The additional supported-input selector permits repeated samples, temporal context and safety fields from the original supported concepts. Derived results are not editable substitutes for their raw inputs.

## Frontend and acquisition
Use the worker result fields directly; do not calculate diagnoses in UI code. `ingest` requires original Measurement and optional Device models, synthetic provenance and immutable device identity. Current UI offers only three reviewed synthetic device policies; it does not assert that real sensors are present. External sensor adapters require separate validation. `monitor` creates the original deterministic cycle; frozen replay recomputes it and must match. A human follow-up completion is not recovery. Management records remain unverified human reports with execution_by_vigile, authorization_by_vigile and efficacy_verified false. Local profile unlock does not establish clinician identity.

UI changes and bindings must preserve explicit UTC timestamps, unit validation, unknown/invalid states, observation identifiers and provenance. No clinical thresholds belong in frontend JavaScript. The compatibility scope is additive worker metadata and the unchanged native backend; the worker is a local capability, not a public HTTP endpoint with write credentials.

## Local AI / RAG
Only the UI grants a model worker bounded read-only context from `assistant_context` and verified public excerpts. Models receive no store, vault keys, backend reader/writer secrets or rule modification capability. `validate_assistant` and `validate_numeric_assistant` run in the biomedical worker after genuine model inference; only their approved sentences are displayed. Numeric text must match original positional facts and finite grammar, including units, owner and frozen run hashes. Dates are displayed separately. Failed/empty/truncated responses yield extractive evidence, not invented missing values. Model metrics mark validation pending until the deterministic validator decides; rejection codes exclude raw private model text.

The current public corpus is eight verified documents (586 sparse blocks); the earlier seven-document/566-chunk corpus is a historical baseline, with scientific authority categories, exact source hashes and quarantine/English presentation guards. Implementation documents and research syntheses are not primary guideline articles. BM25 is original Python; optional MiniLM-L6 vectors cover the verified corpus and fuse with lexical retrieval. Stale/foreign/malformed indexes fall back to lexical retrieval. Model or Internet text never updates a rule or evidence approval.

PubMed is optional, explicit-consent, FULL-mode, fixed-topic metadata only. It does not receive private questions or records; its unreviewed metadata is not fed into clinical rules. Fetch instrumentation is not an independent packet capture or an OS egress firewall. The original WebLLM caches are seeded with SHA-verified pinned public bytes because its internal Cache.add bypasses an overridden fetch. Full public model hashes are verified before runtime initialization; cached ranges are only resumable download material, not trusted executable assets.

## Voice
Explicit local English Vosk capture/file transcription; stop, cancel, lock and optional-worker release must terminate capture. No raw audio is persisted. Typed and voice records remain SELF_REPORTED, never sensor-verified. Automatic saving follows the original opt-in duration-only, past-24-hours, every-word confidence >=0.95 and explicit worker-finalization policy. Physiological readings, symptoms, questions and unresolved transcripts do not qualify. Successful transcription is not successful saving; commit encrypted storage first. Hardware microphone and offline TTS acceptance require separate device tests.

## Reproducibility, storage and resources
The raw SQLite database remains in memory; persistent browser profiles use AES-256-GCM and PBKDF2-SHA256 with 600,000 iterations and random salt/IV. IndexedDB stores ciphertext plus visible labels/metadata. Keep encrypted exports and the passphrase; there is no remote reset. Original Windows SQLite remains unencrypted. Lock terminates private/optional workers and drops references; JavaScript/OS memory erasure is not guaranteed. Same-origin/OS compromise and storage-level audit rewrites/rollback remain outside the chain's guarantees. CAS revisions reject stale writes within an origin; there is no cross-device synchronization/merge.

FULL enables explicit optional models. LOW_POWER/CRITICAL release costly workers and retain deterministic computation and lexical retrieval. These controls do not certify energy/thermal behavior or physical-device model support. Storage includes pinned app assets plus optional model/cache copies and resumable chunks; download size is not total disk/RAM use. A failed optional component must leave the core usable. Do not delete encrypted profiles to repair a public cache.

Read IMPLEMENTATION_STATUS_20261114.md and OFFLINE_INSTALL_AUDIT.md for actual test scopes, observed failures and physical-device acceptance. Software parity and synthetic speech tests do not provide independent clinical or operational validation.

## Reviewed radiation import and local exports

`radiation_preview` accepts the same records as `radiation_import` and returns `{records,count,persisted:false,audit_valid}` after the same normalization/ownership/duplicate checks, without database or audit mutation. Preview IDs are provisional. Commit revalidates against current state and assigns final IDs. No preview token bypasses validation. The UI limits visible preview rows to 10 and requires a separate commit action. Radiation charts keep quantity, unit, mode, quality, instrument, segment and location separate; they do not interpolate intervals or calculate dose. User-initiated history exports are plaintext JSON outside the encrypted vault.


## Additive integration update — 2026-11-15

**USDA catalog v2:** current `nutrition/foods.json` uses `USDA_FDC_FOUNDATION_FOODS_2026_10_ASTHRAL_COMPACT_V2`. `MEAL_NOTE` accepts `nutrition_catalog_id` and `energy_basis`: `DECLARED_1008` (compatibility default), `ATWATER_GENERAL_2047`, or `ATWATER_SPECIFIC_2048`. Reference values are taken from distinct original USDA nutrient IDs, never inferred from macros or substituted automatically. `nutrient_estimate.energy_kcal` uses the explicitly selected method; an absent method stays null even if another method exists. Additive `energy_reference_estimates_kcal` contains all three scaled references. `nutrition_reference` carries method, catalog version, catalog content SHA-256 and source archive SHA-256. The exact v1 catalog remains packaged as `foods-v1.json`; callers may explicitly request `USDA_FDC_FOUNDATION_FOODS_2026_10_ASTHRAL_COMPACT`. Existing stored records are not recalculated. Current default changes catalog ID to v2; consumers comparing the old literal must accept both IDs or explicitly request v1. Legacy `per_100g` values are preserved. Daily energy summaries can combine user-selected reference methods and explicitly disclose this limitation; they do not estimate adequacy or missing intake.

**UTC timelines:** aggregation uses actual UTC dates for timezone-qualified valid timestamps. Invalid/naive timestamps are excluded, not mapped to a normal day. Session checkpoints compare instants, not lexically sorted offset strings. Manual observation forms explicitly request UTC; the earlier form could shift entries by the device timezone. Historical intended timestamps cannot be recovered automatically and are not rewritten. `sleepClockSummary` is descriptive UTC circular-clock dispersion, with null for insufficient or undefined samples; it is not a circadian, recovery or fitness assessment.

**Optional browser MotionGuard:** `training_session.motion_summary` is a validated client report. Inputs name MediaPipe runtime `0.10.21`, pinned Lite model SHA-256, image-plane joint, source hash (local file only), frame/valid/missing counts, nullable min/max angles, optional user-defined cycle boundaries, nullable `cycles`, `observed_complete_cycles`, and timezone-qualified `analyzed_at`. A camera report uses `source: USER_CAMERA_UNVERIFIED`, null file hash, and optional `capture_started_at`. The normalizer returns `source: CLIENT_REPORTED_POSE_ESTIMATE`, `source_kind`, `cycle_status`, and forces execution BLOCKED and all runtime/identity/sensor/temporal-verification flags false. A hash in a client report does not attest that inference happened. No recording date is inferred from processing time. Missing tracking prevents a complete cycle count; observed complete sequences remain separately labelled. Manual activity counts remain independent. Raw media is not placed in the journal. User-initiated JSON exports are plaintext. Model and fixture resources are optional public caches; optional model failure must not disable manual exercise or the deterministic engine.

**DONKI acknowledgement versions:** `noticeState` returns ACKNOWLEDGED, UNACKNOWLEDGED or UPDATED_SINCE_ACK and CURRENT, CHANGED or LEGACY_UNKNOWN revision state. Acknowledgements bind canonical normalized public event metadata, not merely event ID/time. Revised notices require another acknowledgement; older unversioned entries remain visible history. This revision string is not a cryptographic signature or a complete upstream event-body hash. Cache and acknowledgements are public local metadata and do not imply a personal warning or reviewed spaceflight advice.

**Development HTTP policy:** `tools/serve_browser_build.py` mirrors matching rules in the build's `_headers`, including CSP and Permissions Policy, in addition to HTTP/1.1 and explicit module MIME. Camera self permission permits only a normal user-initiated browser prompt; no permission is granted by the application or acceptance scripts. Camera frames/audio are not transmitted. DONKI connect permission is restricted to its official CCMC host. No unsafe-eval, browser security bypass, fake-device flag, or request interception is required for the tested CPU workflows.
